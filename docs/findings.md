# 实际问题、定位与结论

## GPU 运算与环境

先检查已有环境，而非重装。RTX 5060 Laptop 实测 capability=12.0，所选 torch 编译架构含 sm_120；64×64 float32 矩阵乘法与 CPU 整数输入参考结果完全一致。检查脚本与[源环境原始记录公开副本](../results/evidence/gpu-source-env.json)可查。它证明基础 CUDA 运算成功，不独立证明模型能推理。

原实验随后克隆隔离环境，用户亲自运行检查并反馈通过；该次输出来自终端反馈，没有另造独立日志。后续模型运行证据包含实际 torch/GPU 版本。

## Python 输出编码错误

第一次在打印表情时出现 `UnicodeEncodeError: gbk`，尚未调用 generate。[错误记录公开副本](../results/evidence/m1-encoding-error.txt)

使用 `python -X utf8` 解决 Python stdout 编码问题后，PowerShell 管道仍按旧编码解码，导致固定中文和模型回答同时乱码。因此继续对齐当前 PowerShell 的 Console.OutputEncoding 与 OutputEncoding，再重跑。修改仅作用于启动进程和当前终端，无需改模型运算或系统永久配置。

## 单图成功不等于回答可靠

M1 回答正确识别金毛犬，但虚构“双臂举起”，漏掉明显背景，且结尾不完整。原始日志没有保存实际生成 token 数、EOS 或停止原因，不能把结尾不完整确定归因于上限。无需修饰失败回答，它说明链路已经可运行，也说明生成结果需要事实核验。

## 形状证据与源码解释相互补充

64 个图像位置不额外追加到文本序列末尾，而是替换已预留的占位符嵌入；记录显示融合前后均为93位置，具体替换由源码确认。视觉投影输入本来就是张量，它不是“首次把图片转成张量”。

第二次前向输入1个token、已有93位置缓存，未再次触发视觉编码。缓存保存各层的 K/V，而非原始图片。该现象依赖 use_cache=True；关闭缓存不能直接照搬结论。

本次原生 generate 由父类实现，内部直接调用 self.forward；因此仅给顶层 Module 注册普通 forward hook 不能覆盖这个调用。观察脚本临时包装 forward 以记录输入/缓存，并在结束时恢复。

## 尚不能得出的结论

没有正式总体准确率、稳定速度、峰值显存对照或 KV cache 加速比例。M1 日志49.15 tokens/s缺少规范预热、重复和同步计时；65.09M默认排除视觉编码器，不能称作完整系统总参数。没有进行训练、量化或端侧适配。第三阶段不纳入此次展示范围。
